# RS485 on the Waveshare ESP32-S3-Relay-6CH

Findings from bringing up the Soyo/Modbus time multiplex, 2026-08-11.

## Board wiring (both boards)

The onboard transceiver is an **SP3485**:

| Signal | GPIO | Note |
|---|---|---|
| DI (driver in) | GPIO17 | UART TX |
| RO (receiver out) | GPIO18 | UART RX |
| DE + RE | GPIO3 | **already bridged on the board** — DE is active HIGH, RE active LOW, so one pin serves both |

---

## Production board `sofar-waveshare` (192.168.178.187) — receive path is dead

**The UART is configured without a `flow_control_pin`, and nothing in the
configuration ever drives GPIO3.** It is only ever *read*, inside the GPIO scan.
The pin therefore stays at its resting level, which is HIGH. The firmware's own
comment states what that means:

```cpp
// Ruhepegel sofort melden: GPIO3=HIGH → DE/RE=TX → Receiver disabled!
snprintf(init, sizeof(init),
  "init: GPIO3=%d GPIO17=%d GPIO18=%d (3=HIGH→ReceiverOFF!)", ...);
```

With DE permanently asserted the driver is always enabled and the receiver is
always off. Consequences:

* **Transmit works.** Verified on 2026-08-11: a 90 W setpoint sent to the Soyo
  produced −548 / −552 / −659 mA across three parallel battery packs
  (≈ 94 W at 53.38 V), and all three packs switched from `Idle` to `Dischg`.
* **Receive cannot work.** Any reply from a bus device is discarded in hardware
  before it reaches the UART.
* **Modbus (mux channel B) can never complete a transaction** in this
  configuration, no matter how the time slots are arranged. This is a property
  of the direction pin, not of the multiplex.

Status of the claim: the resting level and its meaning are taken from the
firmware's own comment; the absence of any driver for GPIO3 was verified by
searching the whole configuration. It has not been measured with a scope.
It is consistent with the observed behaviour (transmit fine, nothing ever
received).

### Fix — deliberately NOT applied

Production is intentionally left unchanged. The one-line fix would be:

```yaml
uart:
  id: rs485
  tx_pin: GPIO17
  rx_pin: GPIO18
  flow_control_pin: GPIO3   # currently missing
```

`flow_control_pin` makes ESPHome pass the pin as RTS and switch the IDF driver
to `UART_MODE_RS485_HALF_DUPLEX` (see `uart_component_esp_idf.cpp`, the mode is
selected by `flow_control_pin_ != nullptr`). The UART hardware then asserts DE
before the start bit and releases it after the stop bit, bit-exact, with no
lambda involved. The mux needs no change for this: the baud switch calls
`load_settings()`, and that function re-applies pins and RS485 mode every time.

## Test board `rs485defect-wav-esp32s3` — dead chip, external module

The SP3485 branch (GPIO17/18/3) is defective, so the UART was removed from that
board's configuration entirely. Since firmware 1.7 it uses an **external RS485
TTL module** instead:

| Module pin | GPIO |
|---|---|
| DI | GPIO5 |
| RO | GPIO6 |
| DE + RE (bridged) | GPIO4 |

### Wiring — three signal wires per side

```
   ESP32-S3-Relay-6CH                RS485 TTL module             FoxESS T20-G3
   rs485defect-wav-esp32s3           (MAX3485 / SP3485)           COM connector
  ┌───────────────────────┐         ┌────────────────┐           ┌─────────────┐
  │                       │         │                │           │             │
  │   3V3  ●──────────────┼─────────┼─► VCC          │           │             │
  │   GND  ●──────────────┼─────────┼─► GND          │           │             │
  │                       │         │                │           │             │
  │ GPIO5  ●──────────────┼────①────┼─► DI        A ●┼─────④─────┼─● Pin 2  A1 │
  │  (TX)                 │         │                │           │             │
  │ GPIO6  ●◄─────────────┼────②────┼── RO        B ●┼─────⑤─────┼─● Pin 1  B1 │
  │  (RX)                 │         │                │           │             │
  │ GPIO4  ●──────────────┼────③──┬─┼─► DE      GND ●┼─────⑥─────┼─● Pin 5 GND │
  │  (DE)                 │       └─┼─► RE           │           │             │
  └───────────────────────┘         └────────────────┘           └─────────────┘

  ① GPIO5 → DI     transmit data      ④ A → A1   twisted pair with ⑤
  ② RO → GPIO6     receive data       ⑤ B → B1
  ③ GPIO4 → DE+RE  direction          ⑥ GND      signal ground, do not omit
```

The DE/RE bridge belongs on the module — a solder blob or short wire between the
two module pins, then a single wire from there to GPIO4:

| GPIO4 | DE (active HIGH) | RE (active LOW) | Result |
|---|---|---|---|
| HIGH | active | inactive | **transmit**, receiver off |
| LOW | inactive | active | **receive**, driver high-Z |

The UART hardware drives GPIO4 itself in RS485 half-duplex mode; no software
switching is involved.

**Use a 3.3 V module** (MAX3485, SP3485, MAX13487) — *not* a 5 V MAX485 board.
The MAX485 drives RO up to 5 V and GPIO6 is a 3.3 V input; that is out of spec
and can cost the pin. With a 5 V module only, level-shift RO.

Many modules carry a 120 Ω termination resistor, fixed or on a jumper. It belongs
at the end of the bus, not in the middle. The run here is short — the board sees
the stick's AP at −27 dBm, so it sits right next to the inverter.

GPIO17/18/3 are deliberately avoided: the dead SP3485 is still electrically
attached to them and would load or hold the lines depending on its failure mode.
None of GPIO4/5/6 is a strapping pin (those are 0, 3, 45, 46 on the ESP32-S3),
and the board otherwise uses only GPIO 1, 2, 17, 41, 42, 45, 46.

### Bench test over MQTT (no reflash needed)

```bash
# Soyo frame, 10 W
mosquitto_pub -h 192.168.178.218 -t rs485defect-wav-esp32s3/rs485/tx -m 24560021000A80FE

# Modbus FC03, slave 1, registers 0..3 — switch baud rate first
mosquitto_pub -h 192.168.178.218 -t rs485defect-wav-esp32s3/rs485/baud -m 9600
mosquitto_pub -h 192.168.178.218 -t rs485defect-wav-esp32s3/rs485/tx   -m 0103000000044409
```

Replies appear on `rs485defect-wav-esp32s3/rs485/rx` as
`{"len":…,"hex":"…","baud":…}`, frame end detected by a 25 ms character gap.
This is the cheap way to probe the FoxESS slave address and register map without
recompiling. After flashing, the boot log must contain `Flow Control Pin: GPIO4`
— if that line is missing, half-duplex mode is not active.

## Time multiplex (`rs485_mux.h`)

One transceiver, two channels:

* **Channel A** — Soyo, 4800 baud, transmit only, every 3800 ms, always wins.
* **Channel B** — FoxESS Modbus RTU, 9600 baud, inside channel A's gap.

`A_PERIOD_MS` is 3800, not 4000: at 4000 the measured interval was 4003…4047 ms
because the driving lambda runs on a 50 ms interval, and every one of those
values exceeds the Soyo's 4 s timeout. At 3800 the measured interval is
3801…3852 ms, leaving ~150 ms of margin.

Usable window for channel B is `A_PERIOD_MS − A_GUARD_MS` = 3200 ms. Cost of one
Modbus transaction is dominated not by the baud rate but by the 50 ms tick of the
state machine, which emits one action per call:

```
t+  0  A_TX      Soyo frame
t+ 50  BAUD_B    switch to 9600
t+100  B_TX      request out
t+150  response detected
t+200  BAUD_A    back to 4800
t+250  REPORT
```

≈ 250 ms per transaction against a 3200 ms window — a factor of 12 in hand. Pure
transmission time at 9600 baud is 22 ms for 4 registers, 97 ms for 40, and
274 ms for the 125-register FC03 maximum. Note that `rx_buffer_size` is 256
bytes and a maximum-size FC03 reply is 255 bytes, so large reads leave no
headroom.
